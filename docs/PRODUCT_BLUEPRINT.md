# dsh-bot 产品蓝图

本文记录已确认的产品方向与首版范围，供实现和验收使用，不表示这些能力已经实现。当前应用仍为 Electron 桌面骨架；领域名称以 [GLOSSARY.md](../GLOSSARY.md) 为准，当前开发和打包操作见 [README.md](../apps/desktop/README.md)。

## 产品定位

dsh-bot 是以 DeepSeek Harness 为执行基础、支持桌面与移动客户端交互的 Bot 工作台。用户选择具名 Bot 持续对话、观察执行过程并处理工具审批。Runner 是执行状态的权威来源，客户端保存的展示数据不替代执行事实。

每个 Bot 提供一个持续聊天入口，首版关联一个稳定的 Harness Session。首次发送消息前初始化，之后持续复用；初始化失败可以重试，重复请求不得创建额外会话。界面不提供新建或切换 Session，产品 Chat 与执行 Session 仍分别建模。上下文压缩交给 Harness，历史轮换与分支不进入首版。

首版交付 macOS 桌面客户端与本机 Runner，使用 DeepSeek 官方 API。移动客户端作为后续交付目标，只负责输入、展示和授权交互，不运行 Harness，也不取得模型 API Key。

## 宿主与客户端

Runner 独立于桌面 UI 存活。桌面启动先连接已有 Runner，未运行时再启动；退出桌面不停止已接纳工作，停止 Runner 是独立操作。首版要求 Runner 异常退出后自动重新启动，登录自启作为用户可选设置；自动重启不重放输入或工具。macOS 使用用户级 launchd LaunchAgent 管理 Runner；用户主动停止后保持停止，直到再次启动或满足已启用的登录自启条件。Runner 的启动、单实例、本机认证连接、故障拉起和有序停止机制需要在接入验证中落实。

桌面 renderer 继续通过现有 actions、oRPC 与 main 通信，preload 只负责受控端口转发。main 适配与 Runner 的连接及上游 Remote/API；Bot 管理和执行服务不能依赖桌面窗口存活。

产品使用自有 Electron/React 界面，参考官方会话交互，逐项验证上游公开的事件组装和内容呈现能力是否适合复用。官方客户端插件体系及 desktop-host 的进程组织作为参考，具体复用范围需要独立验证。

Web/PWA 采用独立应用入口、构建和发布。桌面与 Web 共用实际相同的聊天、输入、审批、工具结果与附件业务组件，各应用分别组织路由、导航、布局与平台功能；适合共享的完整页面在出现时再提取。原生移动端使用一个 Expo 项目交付 iOS 与 Android。

Harness 引擎经命名 dsh profile 启动，应用配置与插件复用上游扩展机制。模型循环、输入队列、会话日志、权限策略与工具执行继续归 Harness 所有；应用不另建这些机制。

Runner 沿用 Harness Host、Gateway 与标准插件机制，产品插件补充 Bot 管理与生命周期协调。标准 Session Controller 已通过 Host 生命周期扩展接入独立 Runner，确定性模型下的真实进程调用、跟随与配置替换已有契约验证；桌面连接、真实模型与工具、任务操作界面和审批往返仍待应用集成。

## Bot、模板与目录

Bot 保存稳定 ID、名称、工作目录、默认模型及模型参数选择，以及独立拥有的基础指令、补充指令、工具能力与相应插件配置。用户在创建或配置 Bot 时明确选择本地工作目录，界面持续显示当前执行目录；首版不提供会话中途切换目录。工作目录不代表访问授权或 OS 沙箱。

产品里的预设称为 Bot template，是创建 Bot 时使用的内置模板。采用模板时将基础指令、工具与能力组合及相应插件配置具体化为 Bot 自己的配置；后续修改 Bot 不影响模板或其他 Bot，模板更新或移除也不改变已有 Bot。模板来源仅用于说明，不是恢复执行的必需引用。

首版默认模板包含文件读取、编辑和命令执行，应用界面不维护固定工具白名单。Bot 的基础指令在前、补充指令在后共同生效；补充指令不增加该 Bot 配置未开放的工具，也不绕过权限审批。内化的是配置，不冻结插件实现、凭据或引擎版本。

首版通过应用专属配置定义模板，界面提供创建时选择，不提供可视化模板编辑和插件安装管理。已有 Bot 不提供重新套用模板的操作，其后续修改针对自身配置。工具审批界面支持本次允许和拒绝。

Harness Agent preset 是运行时能力组合机制，区别于产品模板。profile 装配进程服务，运行时预设组合相应作用域内的指令和能力；不是所有插件都可按 Bot 独立开关。每个 Bot 使用独立、稳定的运行时预设标识，应用负责从 Bot 配置装配预设；本机组合实验已验证工具隔离，完整 Remote/API 接入仍待验证，见 [Harness 配置接入探索](./HARNESS_INTEGRATION.md)。

恢复已有会话使用 Bot 自身已保存的配置，不重新从模板取值。Bot 配置缺失、无效或所需插件不可用时明确报错，不自动套用默认模板。恢复历史不冻结历史版本的能力代码。

Bot 执行配置在该 Bot 执行中禁止修改；空闲时保存后立即生效，不提供待重启生效状态。保存成功必须表示配置已持久化并已应用；应用失败应明确报错，不得把仅写入文件当作成功。不能立即应用时必须拒绝并说明具体原因，包括仍有待处理输入、维护占用空闲窗口、已有配置变更在进行；不设「已保存待应用」的排队状态，客户端只需区分已生效与未生效。待处理输入只能由用户撤回或等待执行完成，保存不能代为丢弃。Bot 执行配置的修改与新输入接纳需要由 Runner 协调，不能只依赖客户端禁用按钮。

上述协调要求已用状态模型原型验证，见 [生命周期原型记录](./PROTOTYPE_AGENT_LIFECYCLE.md)。

上游已有 Agent 保留绑定的预设版本，保存预设声明不会自动替换其组合。应用持有该 Bot 的 AgentHandle，在无执行和待处理输入时销毁旧 Agent，再用同一 Session ID 与新配置恢复；本机组合实验已验证历史连续和新配置用于下一轮。保存、配置持久化与 Remote/API 并发协调仍需实现验证，不能把核心机制实验等同于产品已完成，详见 [接入探索](./HARNESS_INTEGRATION.md)。

## 输入行为

执行期间的消息处理复用 Harness 的 queue 与 steer 能力，由配置确定默认行为，不在应用代码中固定为只能排队。官方会话插件已有 ui-conversation.busyEnter 设置；本应用如何复用其设置声明与读取方式需要集成验证，不因此直接引入整套官方会话 UI。客户端展示实际提交模式，输入接纳、队列与执行时序由 Harness 管理。

停止当前执行保留 Harness 已接纳的待处理输入，待处理输入后续仍可继续执行。撤回待处理输入是独立操作；界面明确区分停止当前执行、撤回输入与停止 Runner。

## 数据与恢复

dsh-bot 使用独立 Harness home，进一步隔离开发、测试与正式数据。模型凭据交由 Harness 的凭据机制管理，应用不维护第二份权威凭据存储；具体存储提供方和安装包权限需要验证。

引擎异常退出后，客户端明确显示中断，Runner 自动重新启动后允许读取持久历史，不自动重发输入或重复执行工具。恢复历史不承诺继续未完成工具进程，也不承诺任意中断操作可安全重试。

多端共享一个 Runner 的执行事实。客户端断开不停止执行；Runner 离线时的请求保存、投递重试、接纳状态和重复请求处理，需要单独设计并核对 Harness 的接纳机制。

## 多端演进

桌面和移动客户端未来观察与操作同一份工作状态。移动交互先交付独立 Web/PWA，后续用 Expo 交付 iOS 与 Android。客户端共享适用的协议与业务逻辑，各自提供平台适配与界面。模型密钥留在执行侧；首阶段不包含多 Runner 调度、执行迁移或各设备独立执行。

首批移动交付支持选择已有 Bot、发送消息、查看实时回复与历史、查看工具结果、处理审批、停止当前执行和撤回待处理输入。创建 Bot、修改执行配置、模型凭据管理、插件装配和 Runner 维护由桌面优先提供，移动端后续按需求增加。

首批远程能力包含手机上传图片或文件，以及按需查看、下载会话附件与工具产物。传输大小、流量控制和资源访问校验需要设计；大文件断点续传、整目录同步与离线投递另行评估。移动功能范围与页面共享方式分别决定，当前不要求移动端复刻桌面端全部功能。

首批远程连接限本人设备。桌面展示一次性配对二维码或配对码，新设备连接后由桌面确认。每个设备有独立身份，桌面可以查看并撤销；已配对设备获得该 Runner 下全部 Bot 的已确认协作能力，管理操作保留本机桌面。设备认证与业务授权由 Runner 实施，Relay 提供路由与密文转发。

同一待审批操作在多端同时展示时，第一个被 Runner 接受的回答生效，其余设备立即结束该审批并标明已由其他设备处理。迟到的回答被拒绝并给出明确原因，不静默丢弃。多个客户端同时提交执行操作或配置修改时，由 Runner 统一裁决接纳顺序，失败方看到真实结果。

首版通知只包括应用内提示和桌面本机通知；Web Push、原生推送与后台唤醒随移动交付阶段评估，不提前绑定推送服务商。

未来引入 Relay 时，聊天正文、工具结果与审批内容在客户端与 Runner 之间端到端加密，Relay 无法读取这些业务内容。Relay 首次交付要求客户端与 Runner 同时在线，不暂存离线业务请求；只有 Runner 确认接纳后才显示请求已接纳，断连且未收到确认时须保留结果未知状态。Relay 部署、加密与配对的具体协议及同步细节仍需设计。参考项目的 Relay、Outbox 和加密通信实现需要分别评估。

## 工程与升级

产品是独立 Bun 多工作区工程：交互客户端位于 apps/，运行时与有实际消费者的共享包位于 packages/，只维护根 bun.lock。上游源码固定在 references/deepseek-harness 子模块中作为参考，不参与产品构建；引擎通过 packages/harness-runtime 的固定版本 npm 依赖消费，详见 [工程与依赖决策](./PROJECT_LAYOUT.md)。

引擎按发行版升级并验证后随应用发布；参考子模块的更新与运行时升级分别管理。macOS 安装包携带所需运行时，用户无需另行安装 Node、Bun、pnpm 或 dsh。Runner 运行时随桌面安装包一起更新，不提供独立于桌面的升级路径：升级前有序停止 Runner，替换运行时后由 launchd 重新拉起，已接纳但未完成的工作按崩溃恢复规则处理。

升级前备份应用数据，不单独自动升级已安装应用中的引擎。发生持久数据迁移时，不承诺旧版可直接读取迁移后的数据；回退方案必须结合备份与上游兼容性说明。安装位置、签名与升级时的停止时序仍需在真实安装包上验证。

## 首版验收

- 配置 DeepSeek 官方模型，从模板创建或选择 Bot，并明确显示执行目录与当前能力配置。
- 提交消息并实时展示回复，展示文件与命令工具的执行结果。
- 停止当前执行而不关闭 Runner，保留待处理输入；独立撤回待处理输入，完成审批允许、拒绝与请求撤销处理。
- 退出桌面后工作继续，重新打开可连接同一 Runner，重复启动不创建并行实例。
- Runner 异常退出后自动重新启动，客户端可重连并读取历史，不自动重放输入或工具；登录自启可由用户选择。
- 显式停止 Runner 后可以重新启动并读取历史，不通过客户端重放消息恢复执行。
- 同一 Bot 的首次初始化、失败重试与重开均保持唯一 Session 关联，不提供会话切换入口。
- Bot 基础指令与补充指令共同生效，补充指令不能增加工具权限。
- 模板创建的 Bot 配置相互独立；模板更新或移除不改变已有 Bot，也不阻止其历史恢复。
- 执行中拒绝修改 Bot 执行配置；空闲时保存成功后的下一次执行使用新配置，失败不能显示已生效。
- 执行期间发送消息遵循配置的 queue 或 steer 行为，不由客户端另建执行队列。
- 恢复使用 Bot 自身保存的配置；Bot 配置无效或所需插件不可用时报告错误。
- 在无外部 Node、Bun、pnpm 或 dsh 的 macOS 环境中验收安装包。
- 上游升级后重新验证实时回复、停止、审批、历史读取与独立后台生命周期。

## 后续设计与验证

[接入探索](./HARNESS_INTEGRATION.md) 已验证独立预设和同一 Session 上的 Agent 替换机制。首版仍需验证配置保存与恢复协调、官方 Remote/API 的生命周期接入，以及独立 Runner 的生命周期与打包。

多客户端审批竞争、迟到回答、远程连接和移动端机制在进入对应交付阶段时另行设计，不沿用参考项目尚未验证的实现承诺。
