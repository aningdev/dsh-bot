# Bot 配置保存的生命周期原型记录

本次原型回答一个问题：当保存 Bot 配置与执行、待处理输入、维护窗口、冷恢复交错时，Bot 服务允许什么、拒绝什么、客户端看到什么。结论已写入 [产品蓝图](./PRODUCT_BLUEPRINT.md) 的配置段落；本文记录问题、裁决与原型位置。

## 问题

保存配置要求销毁旧 Agent 并在同一 Session 上恢复新 Agent，而销毁会取消并清空 inbox。同时上游只公开两种状态——空闲与执行中——维护期对外仍显示空闲，读取历史还可能触发冷恢复。这些条件叠加后，「保存成功即已生效」是否还成立？

## 裁决

不能立即应用时**直接拒绝并说明原因**，不设「已保存待应用」的排队状态。拒绝原因分为：执行中、仍有待处理输入、维护占用空闲窗口、已有一份配置正在应用、执行已停止接纳。客户端只需区分已生效与未生效两种结果。

曾被考虑并放弃的做法是排队：它会让保存返回成功但配置未生效，直接违反同一条产品要求，并要求客户端多维护一个中间状态。

## 状态模型

| 阶段             | 含义                       | 保存配置                               |
| ---------------- | -------------------------- | -------------------------------------- |
| 尚未初始化       | 没有 Agent                 | 可直接应用：写入配置后用新配置恢复     |
| 空闲             | 无执行、无维护             | 可直接应用：写入 → 销毁旧 Agent → 恢复 |
| 执行中           | 有活动轮次                 | 拒绝                                   |
| 占用空闲期做维护 | 压缩等维护任务持有空闲窗口 | 拒绝                                   |
| 正在更换 Agent   | 已开始替换                 | 拒绝                                   |
| 恢复失败         | 新配置及旧配置恢复均失败   | 停止接纳，报告故障                     |

其余规则同样由模型给出：停止执行保留待处理输入，因此停止后保存仍被拒绝，撤回输入后才能成功；更换期间读取历史被拒绝，避免出现第二个 Agent 所有者；新装配失败时恢复旧配置与旧配置下的 Agent；恢复成功后可继续执行，恢复失败则停止接纳，客户端不得显示新配置已生效。

## 原型位置

- 分支：`prototype/agent-lifecycle`
- 文件：`packages/bot/prototype/agent-lifecycle.html`
- 运行：直接用浏览器打开该文件，无需依赖或服务

文件包含一个纯逻辑模块（`(state, action) => state`，不接触 DOM，可整块搬进实现）和一个供点击的页面：状态面板、自由操作按钮、六个场景（正常保存、执行中保存、待处理输入挡住保存、维护期保存、冷恢复撞上更换、装配失败）。

## 边界

此原型验证的是**协调规则**，不是 API 可行性。官方 Session Controller 自行恢复 Agent 而不交出句柄，这一冲突仍未通过真实代码验证；原型的阶段模型假定应用能够独占替换 Agent。若该假定不成立，阶段划分不变，但「正在更换 Agent」由谁驱动需要重新确定。

原型未覆盖多个客户端同时保存、持久化中断、真实维护与模型执行。#4 的公开接口测试已验证五种拒绝、并发保存、真正的维护占用、同一 Session 替换、失败回退及未完成事务在 Host 重启后的停止接纳；真实 Node Remote 测试覆盖配置应用与进程重启。实现与验证范围见 [Bot 插件](../packages/bot/README.md) 和 [Runner](../apps/runner/README.md)。真实模型、保存中途强制终止进程和官方 Session Controller 共存仍未验证。
